제7부: 무엇을 추출해 자기 플러그인으로 옮길 것인가

29장: 오마오가 플러그인 하니스로서 잘하는 것

온라인판은 책의 질문과 해석 순서를 유지하면서 현재 fork의 실제 소스 경로와 링크를 함께 제공합니다.

현재 fork 기준 보정

이 온라인판은 원고의 관점과 장 구성을 유지하지만, 현재 speaky-oh-my-openagent 포크의 리팩터링을 기준으로 소스 경로를 보정합니다. 원고의 오래된 src/... 참조는 가능한 경우 packages/omo-opencode/src/...로 해석합니다.

루트 src/는 더 이상 canonical source tree가 아니며, OpenCode 어댑터는 packages/omo-opencode/src/, Codex Light edition은 packages/omo-codex/, 공유 core는 packages/*-core/에 분리되어 있습니다.

오마오의 장점은 기능이 많다는 사실보다 기능을 OpenCode plugin contract 안에 비교적 선명하게 배치한다는 점이다. 에이전트는 agent config로, 실행 능력은 tool로, 생명주기 개입은 hook으로, 외부 protocol은 MCP로, 호환성은 loader와 transformer로 분리한다.

잘하는 점 1: 초기화 순서가 설계를 설명한다

src/index.ts의 5단계는 책 전체를 요약한다. config, manager, tool, hook, interface가 순서대로 만들어진다. 큰 플러그인에서 entry point가 순서를 설명하는 것은 중요하다.

잘하는 점 2: 설정 의미론이 명확하다

deep merge할 필드와 set union할 필드가 구분된다. partial parse와 migration도 있다. 사용자 로컬 환경에서 실행되는 플러그인에게 이 관대함과 명확성은 실용적이다.

잘하는 점 3: 확장 계약을 섞지 않는다

스킬을 도구로 흡수하지 않고, skill MCP를 전역 MCP와 분리한다. Claude Code 호환성도 core logic이 아니라 loader와 hook 계층으로 둔다. 확장을 많이 제공하면서도 각 확장의 lifetime을 다르게 본다.

잘하는 점 4: 장기 실행을 상태로 다룬다

background manager, tmux manager, continuation hook, stop guard, notification이 함께 있다. 긴 작업을 prompt로만 해결하지 않고 실행 경로와 관찰 표면을 만든다.

잘하는 점 5: 실패를 숨기지 않는다

fallback, toast, title 표시, log, doctor는 모두 자동화의 실패를 드러내는 장치다. 플러그인이 복잡해질수록 이런 표면이 필요하다.

남는 부채

기능 수가 많아질수록 설정과 hook interaction을 이해하기 어렵다. 일부 compatibility layer는 OpenCode native 기능이 늘어날수록 계속 재평가해야 한다. 도구와 훅이 많기 때문에 provider별 tool cap이나 모델별 tool 선택 품질도 지속적으로 관리해야 한다.

핵심 코드

오마오가 잘하는 점은 이 작은 조립 코드에 압축되어 있다. src/create-hooks.ts는 hook을 기능 목록으로 두지 않고 tier별 결과로 합친다.

export function createHooks(args: {
  ctx: PluginContext
  pluginConfig: OhMyOpenCodeConfig
  modelCacheState: ModelCacheState
  backgroundManager: BackgroundManager
  modelFallbackControllerAccessor?: ModelFallbackControllerAccessor
  isHookEnabled: (hookName: HookName) => boolean
  safeHookEnabled: boolean
  mergedSkills: LoadedSkill[]
  availableSkills: AvailableSkill[]
}) {
  const core = createCoreHooks({ ... })
  const continuation = createContinuationHooks({
    ...,
    sessionRecovery: core.sessionRecovery,
  })
  const skill = createSkillHooks({ ... })

  const hooks = {
    ...core,
    ...continuation,
    ...skill,
  }

  return {
    ...hooks,
    disposeHooks: (): void => {
      disposeCreatedHooks(hooks)
    },
  }
}

소스 그라운딩

  • entry point는 5단계지만, 실제 행동은 src/plugin-handlers, src/plugin/hooks, src/tools, src/features, src/agents로 분산된다. 이 분산은 모듈 경계를 만들지만 독서 비용을 높인다.
  • HookNameSchema의 hook 수와 tool-registry의 tool 수가 모두 많기 때문에 disabled_hooks, disabled_tools, experimental.max_tools가 단순 옵션이 아니라 운영 필드가 된다.
  • Sisyphus 중심 경로는 applyAgentConfig()에서 default agent까지 바꾼다. 오마오는 보조 plugin이 아니라 OpenCode agent selection 정책까지 적극적으로 건드린다.
  • Claude Code 호환성은 agent, command, MCP, plugin component, hook까지 여러 loader로 퍼져 있다. 강력하지만 OpenCode native 변화에 계속 반응해야 한다.
  • background manager는 depth limit, concurrency, task history, polling, fallback retry, toast, cleanup까지 품는다. 이 장점은 동시에 큰 manager의 부채다.

빌더에게 남는 것

오마오를 그대로 복제할 필요는 없다. 가져갈 것은 기능 수가 아니라 경계다. 초기화 순서, 설정 의미론, 확장 계약 분리, 장기 실행 상태, fallback 관찰성은 작은 플러그인에도 그대로 적용된다.
